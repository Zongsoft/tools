# Migration implementation

Database configuration is parsed by MigrationLoader.Databases. [Zongsoft.Core](https://github.com/Zongsoft/framework/tree/main/Zongsoft.Core) resolves entries/import overrides; a local [Zongsoft.Core](https://github.com/Zongsoft/framework/tree/main/Zongsoft.Core) view without imports supplies declaration locations for ordered events and genuinely empty sections. Effective entries retain first position and final origin. Provider.Prepare fills creation defaults before fingerprints. The plan separates Databases (administrator parameters, effective options, users) from ordered Steps referencing zero-based Databases array indexes. Only referenced targets enter the plan. Executor validates all SQL first, then initializes every database, creates every account/mapping, executes tasks, and appends grants. Existing settings/passwords remain unchanged. Database pending records contain only target/settings hashes and resume unfinished creation settings. Amazon S3 keeps its existing parsing and execution. See the [database reference](../README.md#database-configuration).

MySQL provider defaults are `Secured=false` and `AllowPublicKeyRetrieval=true`; `Prepare` records both in the plan before fingerprinting. The executor maps `Secured` to `SslMode=Disabled` or `Required` and passes the effective public-key retrieval setting to MySqlConnector for every administrator/database connection. Explicit values are retained; `AllowPublicKeyRetrieval` is a MySQL-only Boolean parameter.

The generator src uses [Zongsoft.Core](https://github.com/Zongsoft/framework/tree/main/Zongsoft.Core) Profile and Searcher for input. MigrationLoader.Database prepares SQL batches; AmazonS3 parses bucket options. MigrationBundle collects the complete native publication and plan. Generator writes PAX tar using System.Formats.Tar, recording Migrator (assembly@version) and Runtime metadata. No project references packager.

Before version resolution, shared `Utility.CreateVariables` loads defaults, environment values, direct `.env` files from the filesystem root to the working directory, and explicit options. `Utility.LoadEnvironmentVariables` uses `Profile.Load`, joining recursive section levels and entry names with `_` while preserving root names, null/empty values and [Zongsoft.Core](https://github.com/Zongsoft/framework/tree/main/Zongsoft.Core) imports. Only missing files at the open stage are skipped; other read/parse failures propagate. Values remain lazy and invocation-scoped; the process environment is unchanged. All input files share this variable view, regardless of their own directories.

`Variables.From` declares `FRAMEWORK` in a case-insensitive set passed as `fallbackOptions` to shared `Utility.CreateVariables`. The existing option merge loop preserves an existing nonempty variable only when a declared option has a raw null/empty value. Without a nonempty fallback, the original assignment remains so an explicitly empty variable still expands to empty. Whitespace options, expressions that expand to empty, and nearer `.env` values that clear earlier values keep their existing behavior. Framework remains a general variable and does not select the native executor or RID.

Database and Amazon S3 parameter lookup uses `<input-name>.ini`, then provider aliases such as `postgres.ini` and `postgresql.ini`, at each directory from the declaration source to the root. It selects the nearest applicable complete configuration and merges only explicit imports. Diagnostics separate source locations from reasons on the next line and list candidate parameter files one per line in lookup order. Shared `Utility.Indent` preserves nested detail indentation and uses platform line endings. Automatic lookup no longer falls back to `*.env`; existing parameter fixtures, examples and import paths use `.ini`. Generic `.env` variable inheritance does not merge connection configurations.

`MigrateCommand.Version.cs` contains the private `VersionSource` nested type. The command removes implicit environment/`.env` version and Edition values, taking these options only from the command line. The resolver expands the version input and gives numeric versions priority. Default/explicit directories open their direct `.edition` with `ApplicationManifest.Load(Stream)`; only a missing manifest permits `.version` with `ApplicationIdentifier.Load(Stream)`. Explicit file names ending in `.version` use the identifier reader (case-insensitive); other names use the manifest reader. Read/format failures retain the full path and never try another parser.

Source selection and artifact Edition are separate. Explicit nonblank Edition selects a manifest entry with canonical spelling; otherwise Current, the only Edition, or the top-level version supplies the version number only. Multiple Editions without Current require a selection. An identifier supplies its version, while explicit Edition may add or replace its Edition. Without explicit Edition the final artifact Edition is null, even for numeric versions or a named Current. Final versions must be nonzero. Files are never saved, including Current; legacy multi-Edition `.version` files require renaming to `.edition`.

The process entry uses `tools/.shared/Utility.cs` to preserve each argument boundary and escape backslashes, including empty values and Windows paths with spaces. Options that may contain variables enter the command as strings. After resolving the version source, the command writes the final version and Edition into a per-invocation `Variables` view; other values expand recursively when used, before type conversion. [Zongsoft.Core](https://github.com/Zongsoft/framework/tree/main/Zongsoft.Core)'s `Switch` evaluates Boolean options. Enums use [Zongsoft.Core](https://github.com/Zongsoft/framework/tree/main/Zongsoft.Core) conversion without an additional member-definition check. `--name` is independent of the version file; input/output paths use the working directory. No save operation is performed. The plan protocol and native executor do not participate in source version lookup; they receive the final identity. Command tests cover literal/file/directory/default sources, Edition selection, variable expansion and unchanged source/output files on failures.

.shared compiles into the generator and executor through source links, without a shared DLL. MigrationPlan uses partial and nested Step/Script/Bucket/Database/User models and source-generated JSON. Source/Content only exist on the generation side. Shared code validates provider parameters and plan structure. See the [package details](../README.md#advanced-package-details) for plan fields and fingerprints.

The executor explicitly selects one of six databases or Amazon S3, and owns connections, initialization, ordered submission, checksums, locks, state and pending records. Every apply executes all SQL without per-file history. Only the executor declares database/AWS dependencies; TDengine uses WebSocket directly.

The external launcher and archive use the identical stem `<name>[-<edition>](migrate)@<version>_<RID>`, using the input name verbatim and omitting the Edition segment when absent. Plan names and default state directories retain their existing migration suffix normalization so persistent state remains reusable. Generation embeds the exact archive name, version-independent state name and plan fingerprint in the launcher. Its second argument overrides the state directory. Check only compares ready; apply/status extract the archive directly into a unique temporary directory, invoke `migrate.sh` or `migrate.cmd` at that directory's root with the action and persistent state, propagate the exit code and clean up. Packager installation and systemd gates invoke this external entry without interpreting SQL or plan fields.

Both outputs use `tools/.shared/ArtifactPublisher.cs` to stage privately under the destination before backup/replacement. Failures restore prior outputs. The same class also handles single-file writes and copies in the other tools, using atomic replacement for one file. The generator also links shared variable source and `Utility.cs`, which compiles into this project's `partial Utility`; no shared DLL or executor protocol change is involved. The archive root contains `migration.json`, `id`, the internal entry script, the native executor and its dependencies; SQL paths are `.artifacts/<provider>/<sequence>.sql`, relative to that root. The executor uses the plan file's directory as its working root and permits SQL only within its `.artifacts/` subtree. Plan paths participate in the fingerprint. The generator, launcher and executor must use this same layout. Inside the archive, migration.json is 0600, other data 0644 and entries 0755. On Unix the external archive is 0600 and launcher 0755. Expanded credentials are included; do not publish such archives publicly.

Linux needs glibc >=2.34, libgcc, libstdc++, zlib, ICU, OpenSSL and CA certificates; some authentication needs Kerberos/GSSAPI. Shell execution needs sh, tar/gzip, core utilities and cmp. Windows needs system PowerShell, tar.exe and the bundled native DLLs. Targets need no .NET runtime. AOT preserves globalization and English/Chinese resources; publications reside in `executor/src/bin/<Configuration>/net10.0/<RID>/publish/`, with logs/ and symbols/ alongside that directory. Build and standalone publish outputs link native files into .migrator/<RID>/ beside the generator. NuGet packaging stores them once at tools/.migrator/<RID>/ and removes the per-framework copies from the package. MigrationBundle first checks the local .migrator/ directory, then the shared directory two levels above tools/<TFM>/any/. Source directories do not receive native output. Third-party warnings remain visible and reviewed.

Common package versions come from the repository root Directory.Packages.props; database drivers and AWS SDK versions remain in the executor project through VersionOverride. All projects use the CodeAnalysis version defined in the root Directory.Packages.props with strict builds and a separate IDE0049 verification. Resources use ResXFileCodeGenerator; no localization tests. Ordinary builds neither require packager nor start containers.

MigrationPlan exposes Name (the normalized migration name, recorded as name in status), Steps and Databases; both Step and Database use Settings for connection settings. Steps have no Id; the executor sets MigrationContext.StepNumber from array position. Database has no Id; Step.DatabaseIndex references the zero-based position in Databases. Validation checks bounds and provider agreement before any external operation. Amazon S3 omits DatabaseIndex. Database initialization, execution and status use the same index; status records it as databaseIndex. Deduplication and pending recovery still use the actual target key, independent of array position. The formatted serialization context copies Serialization.Default.Options, including WhenWritingNull, so compact fingerprint and formatted output share null handling without repeating member attributes. SQL artifact numbers are unpadded; list order remains authoritative.

## Native AOT build scripts

Build scripts reside in executor/build:

- `setup.sh` prepares the dedicated Rocky Linux 9 x64 container: it installs compiler tools and development libraries, downloads and verifies the .NET SDK version configured in the script, and extracts ARM64 RPMs into /aot/sysroots/linux-arm64 to supply cross-compilation headers, libraries and startup objects. Caches persist under /aot; ARM64 package installation scripts are not executed.
- `clang-arm64.sh` wraps clang for ARM64 cross-compilation: it disables the host's default clang configuration, selects the GCC directory in the ARM64 sysroot and forwards compiler arguments. publish.sh uses it with SysRoot and CppCompilerAndLinker to avoid linking against the host x64 toolchain.
- `publish.sh` keeps Linux x64/arm64 compilation caches under /aot, verifies outputs, then copies the complete publication to the corresponding executor publish/ directory in the workspace; symbols are stored separately.
- `publish.ps1` uses the SDK default publish/ directory for win-x64 on Windows, checks PE architecture and separates symbols from the publication.

These scripts are build-time tools; they are not executed on migration target machines.

## Native AOT validation

After publication, inspect ELF/PE architecture, native dependencies, globalization resources and Linux executable modes. On isolated targets without .NET, validate SQLite/DuckDB apply/status/check, repeat runs, failure/retry, locking, temporary-directory cleanup and persistent state across versions. ARM64 validation may be limited to compilation and architecture checks.

Fixed dependency versions produce trimming and dynamic-code warnings in SqlClient diagnostics, reflective configuration, SQL CLR types and parameter conversion; ConfigurationManager reflection; DuckDB complex collection/structure conversions; and MySqlConnector diagnostics. Full logs are in `executor/src/bin/<Configuration>/net10.0/<RID>/logs/publish.log`. Keep and review individual warnings. Successful compilation or native publication does not establish that advanced driver features work. Validate network authentication, complex types and real Amazon S3 services for the intended scenarios.

Generator tests cover input, SQL batches, naming, overwrite recovery and process handoff. Executor tests cover plan validation, database execution, state, Amazon S3 pending and TDengine sessions. See [README](../README.md#build-and-test) for commands.

MigrationPrivileges canonicalizes the 20 capability names and expands Permission into the effective plan array before fingerprinting. Drivers deduplicate native grants, add connection/schema/sequence dependencies, and keep new grants inside the target database. MySQL validates role SHOW GRANTS; PostgreSQL validates role dependencies through pg_shdepend and checks object ownership for DDL; SQL Server grants database/schema/object permissions directly. Only the internally constructed MigrationPrivilegeException may expose its sanitized capability context in executor status; server exceptions still report type only. See the [database reference](../README.md#database-configuration) for future-object and native granularity limits.
